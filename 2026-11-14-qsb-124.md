We have published [Qubes Security Bulletin (QSB) 124: Partial filtering bypass in split-gpg2](https://github.com/QubesOS/qubes-secpack/blob/5ac7d837cdd0777d982db257e15252e7a9cae7cb/QSBs/qsb-124-2026.txt). The text of this QSB and its accompanying cryptographic signatures are reproduced below, followed by a general explanation of this announcement and authentication instructions.

## Qubes Security Bulletin 124

```

             ---===[ Qubes Security Bulletin 124 ]===---

                             2026-11-13

                Partial filtering bypass in split-gpg2

User action
------------

Continue to update normally via the Qubes Update tool or its
command-line equivalents [1] in order to apply the security updates
described in the "Patching" section below.

Summary
--------

Split-gpg2 filters incoming gpg-agent commands by parsing them and then
reconstructing allowed commands, in some cases by removing or replacing
some of their parts. Due to a bug, it is possible for lines to be sent
that exceed the line length limit of the protocol. Combined with GnuPG's
handling of such overlong lines, this allows commands to be injected
that split-gpg2's filtering would normally not allow.

Impact
-------

In the supported split-gpg2 configuration, a malicious qube can cause
the gpg-agent to display a password prompt with arbitrary text and
receive the response that the user enters. Such a prompt would have the
window borders of the backend (for example, vault) qube, so an attacker
could use this to try to trick the user into entering a passphrase.

However, if the user's PGP key does not have a passphrase, then such a
request might not make sense (e.g., the user might be confused about the
passphrase being requested and may not have one to provide). Moreover,
in the supported configuration, the vulnerability under discussion does
not allow for extracting or manipulating secret keys, since split-gpg2
uses an "extra" gpg-agent socket that has limited capabilities.
Therefore, even if the user's PGP key does have a passphrase, and even
if the attacker manages to steal that passphrase, the passphrase should
be useless to the attacker without the secret key.

In theory, this vulnerability could also be used to exploit some further
hypothetical GnuPG vulnerability that normally would have been prevented
by split-gpg2's filtering.

Affected systems
-----------------

All supported Qubes OS releases are affected. Only users of split-gpg2
(i.e., the `split-gpg2` package) are affected. All recent versions of
split-gpg2 are affected.

Note: split-gpg2 is a distinct component from split-gpg1 (i.e., the
`qubes-gpg-split` package).

Technical details
------------------

When checking incoming "D" commands in response to an "INQUIRY" from the
gpg-agent, split-gpg2 allows unescaped "%" characters. When sending
these to the gpg-agent, split-gpg2 correctly escapes them ("%25") as
required by the protocol. This increases the lengths of lines containing
such characters. Therefore, split-gpg2 can send lines that exceed the
line length limit (which it correctly checks on incoming lines).

When receiving overlong lines, the behavior of GnuPG's gpg-agent
implementation depends on the context. For normal commands, they are
treated as fatal errors. However, for "INQUIRY" responses, the command
that initiated the "INQUIRY" is simply aborted with an error response.
The part of the line exceeding the limit is then treated as a new line
that is parsed normally as a command.

While the vulnerability under discussion does not allow an attacker to
extract secret keys in the supported configuration, it is possible for
the user to manually set up an unsupported configuration that does allow
an attacker to extract secret keys. In particular, the user can enable
the `allow_keygen` option in the split-gpg2 config, as documented in the
README [5]:

    ## Allow key generation

    By setting `allow_keygen = yes` in `qubes-split-gpg2.conf` you can
    allow the client to generate new keys. Normal usage should not need
    this.

    **Warning**: This feature is new and not much tested. Therefore it's
    not security supported!

Again, as stated in the quoted text above, this configuration is not
security supported. It is mentionned here only for the sake of
completeness.

Patching
---------

The following packages contain security updates that address the
vulnerabilities described in this bulletin:

  For Qubes 4.3, in templates used for split-gpg2:
  - split-gpg2 package, version 1.1.16

These packages will migrate from the security-testing repositories to
the current (stable) repositories after being tested by the community.
This testing period is intended to catch bugs affecting Qubes OS
stability before the packages reach the broader userbase. By default,
the security-testing repositories are disabled in both dom0 and
templates. If you wish to receive security updates faster at the risk of
encountering more bugs, you can enable the security-testing repositories
either temporarily (for a single update) or permanently. [2] Dom0,
templates, and standalones each have their own security-testing
repositories, which can be enabled independently of one another. [3][4]
If you do not have the relevant security-testing repositories enabled
while security updates are in security-testing, you must wait until they
migrate to the current (stable) repositories, which generally takes one
to two weeks but may be expedited in urgent cases. Once the packages are
available to your Qubes OS system, you should install them as described
in the "User action" section above.

After you have installed the packages listed above, you must shut down
the relevant templates and restart all split-gpg2 backend qubes.
```

## What is the purpose of this announcement?

The purpose of this announcement is to inform the Qubes community that a new Qubes security bulletin (QSB) has been published.

## What is a Qubes security bulletin (QSB)?

A [Qubes security bulletin (QSB)](https://www.qubes-os.org/security/qsb/) is a security announcement issued by the [Qubes security team](https://doc.qubes-os.org/en/latest/project-security/security.html#qubes-security-team). A QSB typically provides a summary and impact analysis of one or more recently-discovered software vulnerabilities, including details about patching to address them.

## Why should I care about QSBs?

QSBs tell you what actions you must take in order to protect yourself from recently-discovered security vulnerabilities. In most cases, security vulnerabilities are addressed by [updating normally](https://doc.qubes-os.org/en/latest/user/how-to-guides/how-to-update.html). However, in some cases, special user action is required. In all cases, the required actions are detailed in QSBs.

## What are the PGP signatures that accompany QSBs?

A [PGP](https://en.wikipedia.org/wiki/Pretty_Good_Privacy) signature is a cryptographic [digital signature](https://en.wikipedia.org/wiki/Digital_signature) made in accordance with the [OpenPGP](https://en.wikipedia.org/wiki/Pretty_Good_Privacy#OpenPGP) standard. PGP signatures can be cryptographically verified with programs like [GNU Privacy Guard (GPG)](https://gnupg.org/). The Qubes security team cryptographically signs all QSBs so that Qubes users have a reliable way to check whether QSBs are genuine. The only way to be certain that a QSB is authentic is by verifying its PGP signatures.

## Why should I care whether a QSB is authentic?

A forged QSB could deceive you into taking actions that adversely affect the security of your Qubes OS system, such as installing malware or making configuration changes that render your system vulnerable to attack. Falsified QSBs could sow fear, uncertainty, and doubt about the security of Qubes OS or the status of the Qubes OS Project.

## How do I verify the PGP signatures on a QSB?

The following command-line instructions assume a Linux system with `git` and `gpg` installed. (For Windows and Mac options, see [OpenPGP software](https://doc.qubes-os.org/en/latest/project-security/verifying-signatures.html#openpgp-software).)

1. Obtain the Qubes Master Signing Key (QMSK), e.g.:

   ```shell_session
   $ gpg --fetch-keys https://keys.qubes-os.org/keys/qubes-master-signing-key.asc
   gpg: directory '/home/user/.gnupg' created
   gpg: keybox '/home/user/.gnupg/pubring.kbx' created
   gpg: requesting key from 'https://keys.qubes-os.org/keys/qubes-master-signing-key.asc'
   gpg: /home/user/.gnupg/trustdb.gpg: trustdb created
   gpg: key DDFA1A3E36879494: public key "Qubes Master Signing Key" imported
   gpg: Total number processed: 1
   gpg:               imported: 1
   ```

   (For more ways to obtain the QMSK, see [How to import and authenticate the Qubes Master Signing Key](https://doc.qubes-os.org/en/latest/project-security/verifying-signatures.html#how-to-import-and-authenticate-the-qubes-master-signing-key).)

2. View the fingerprint of the PGP key you just imported. (Note: `gpg>` indicates a prompt inside of the GnuPG program. Type what appears after it when prompted.)

   ```shell_session
   $ gpg --edit-key 0x427F11FD0FAA4B080123F01CDDFA1A3E36879494

   This is free software: you are free to change and redistribute it.
   There is NO WARRANTY, to the extent permitted by law.

        created: 2010-04-01  expires: never       usage: SC
        trust: unknown       validity: unknown

   pub   rsa4096/DDFA1A3E36879494 2010-04-01 Qubes Master Signing Key
    Primary key fingerprint: 427F 11FD 0FAA 4B08 0123  F01C DDFA 1A3E 3687 9494
   ```

3. **Important:** At this point, you still don't know whether the key you just imported is the genuine QMSK or a forgery. In order for this entire procedure to provide meaningful security benefits, you *must* authenticate the QMSK out-of-band. **Do not skip this step!** The standard method is to obtain the QMSK fingerprint from *multiple independent sources in several different ways* and check to see whether they match the key you just imported. For more information, see [How to import and authenticate the Qubes Master Signing Key](https://doc.qubes-os.org/en/latest/project-security/verifying-signatures.html#how-to-import-and-authenticate-the-qubes-master-signing-key).

   **Tip:** After you have authenticated the QMSK out-of-band to your satisfaction, record the QMSK fingerprint in a safe place (or several) so that you don't have to repeat this step in the future.

4. Once you are satisfied that you have the genuine QMSK, set its trust level to 5 ("ultimate"), then quit GnuPG with `q`.
